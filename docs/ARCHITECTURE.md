# Working on the card club

## Start here

Read PRODUCT.md for intent and DESIGN.md for the shipped visual language. Keep rule decisions in the engine, turn ownership in the hooks/server, and presentation in components. Don’t restart the project to change its look.

## State and actions

Controllers stamp `GameState.roundId` and `tableScore` using `startTableRound`. Engine actions preserve this optional JSON metadata. Local deals generate device-local round identities; online deals use secure random bytes. `recordTableWin` increments exactly once for a round whose declared winner has an empty hand. Result publication, metadata updates, duplicate packets and reconnects cannot increment the same result twice. Device-local `recordRound` also uses round identity when available, retaining its legacy snapshot fallback.

The score counts completed-round wins for one crew, with no point valuation, finishing ranks or account standing. Local One more round carries it through a dedicated rematch action, while a fresh start resets it. Validated unfinished saves preserve both identity and score; malformed score data is discarded without losing the hand. Completed local result screens follow the existing unsaved-result boundary, while lifetime device progress remains recorded. Online rooms keep the completed score outside the current game so Edit table can preserve it through rule edits. Actual lobby joins, removals and bot-seat changes clear the score; reconnecting the same device does not. New deals include the prior valid score for the unchanged roster. The public projection includes only win counts and opaque round identities, retaining hand privacy and legacy client compatibility.

`TableScoreCard` reuses the native result rows in results, table activity and the online lobby. Results prioritize current-crew wins, with terminal card counts in a native disclosure; older servers without score metadata retain the original result summary. Short landscape omits redundant winner artwork when scores are present, keeping actual totals and rematch decisions accessible. Existing modal content scrolling bounds six-seat results; no persistent game HUD is added.

`lib/gameActions.ts` accepts and returns serializable, immutable `GameState` snapshots. Local games use `useUnoGame`; online games use `useUnoOnlineGame`, backed by server acknowledgements and `room:update` events. GameBoard accepts their shared API union without pretending the online API is local.

Opening discards always have a real color; rejected wilds return to the deck. Colored opening actions apply their skip, reverse, or draw effect. A local game has one human. The online server checks room membership and turn ownership. Jump-in is validated against an exact matching card. A wild must receive one of the four real colors, including when it is a winning card. UNO declarations and call-outs are metadata actions; they must not clear the local voluntary-draw/pass state.

Online room seat IDs can differ from array positions after kicking/replacing players. Initialization explicitly maps game players back to room IDs. Never assume `player_1` is array index 1.

## Timing

`GameRules.botDifficulty` selects Casual, Standard or Tactical card decisions in the shared `getBotMove` strategy. Rule validation rejects unknown values; older rules default to Standard. Casual takes the first legal card, Standard retains the original greedy ranking, and Tactical values color continuity, wild conservation, actual Discard All shedding, shuffle hand-count estimates and threats in the current direction. Tactical never reads an opponent’s card faces or the draw pile. `check-bot-difficulty` compares every recommendation against a recipient-only view across all presets and levels, and checks complete rounds, legality, immutable inputs and deck conservation. Bot pacing, automatic UNO declarations, penalties and human clocks are unchanged.

The native BotDifficultyControl is shared by bot options, host table rules and Settings. Difficulty is excluded from preset identity and preserved by preset switches. Preferences apply to future tables; saved rounds and rematches retain their own rules. Online guests see the published challenge when the room has bot seats, and the game menu names the active challenge. Both local and server controllers already call the shared strategy, so the setting does not introduce a second bot loop or client-authoritative online actions.

Local and online bots wait about 760 ms. The online server publishes the triggering human action before scheduling one automated turn; it does not run a synchronous chain that hides intermediate actions. A pending callback rechecks current state and connection status before acting.

Human turns start with a 30-second controller-owned deadline. Missing it marks the human seat in `autoPlayPlayerIds` and uses the same `playBotStep` strategy as regular bots, including legal stacks, wild colors and UNO declarations. Subsequent unattended turns get 10 seconds. A bot draw is published separately and finishes after normal bot pacing; it cannot repeatedly reuse an expired deadline. Unavoidable forced draws retain their short delay without marking a player away. Pointer/keyboard activity, returning to a visible tab, a valid manual game action or online rejoin restores that seat's control and gives its active turn a fresh 30 seconds. Other seats' deadlines are preserved. A local saved-round resume also restores human control. The server owns online clocks; clients report only their own activity through authenticated membership.

A voluntary human draw with no playable option automatically passes after a short delay. A playable draw leaves the choice to the player. Online disconnected seats are temporarily driven by bots while other humans remain. If no humans are connected, bot progression stops and the room has a 45-second reconnect window.

## Audio and motion

`useGamePresentation` compares snapshots, animates transforms using the Web Animations API, and plays feedback during the same transition. Nothing awaits an animation or audio duration before changing game state. Never bring back `getBoardVoiceRemainingMs()` or queue narration behind old actions.

`tableChimes` owns one interactive AudioContext, a decoded 280 ms recorded card sound, and an immediately available procedural fallback. Gesture unlock starts a one-frame silent buffer and resumes suspended/interrupted contexts. The latest action may survive an in-flight unlock for at most 160 ms; older actions and hidden-tab feedback are dropped. Playback never waits for fetching or decoding. The table subscribes to audio readiness and reflects effective card-sound preferences; enabling sound restores disabled effects/zero volume without changing optional voice or music. Volume, voice, card sounds, optional music, and master mute are independent preferences. `useAudioManager` owns only background music and gesture/settings subscriptions.

Voice assets are preloaded when enabled, use normalized compressed files, and expire if they cannot start promptly. A newer action, mute, hidden document, or leaving the board stops the old voice. Original WAVs remain source material, not runtime requests.

The presentation hook cancels animations and removes temporary flight nodes on unmount. Reduced motion uses state changes without travel. Do not animate `left`, `top`, or layout dimensions frame by frame. Opponent flights use a visible native fan card as their pose; compact phones hide those fans, so the visible avatar supplies the pose instead. A drawn card always clones the face-down deck and scales its geometry and card lettering into that destination; the avatar is never cloned as a card. The loopback-only card-continuity fixture records both directions against published engine snapshots.

## Reconnect and storage

`server/friendStore.ts` owns device-bound accepted friendships, public profile records and pending requests. `social:request`, `social:respond`, `social:remove` and `social:sync` require registered socket presence; only the request recipient can accept, and only accepted friends can receive `friend:invite` room invitations. Public social snapshots never expose device identities. Friend requests last 30 days, pending counts and accepted lists are bounded, and JSON writes replace an atomic temporary file before committing memory. The default `.data/friends.json` is ignored by Git; set `UNO_SOCIAL_FILE` to a file on a persistent volume when deploying the single socket process. Do not share that file between multiple server processes. Clearing a browser's device identity is not recoverable through an account login.

`ProfileMenu` provides the same native avatar popover in home, setup, rooms and play. The wide account modal is loaded only when opened; only its selected Profile/Friends/Game/Audio/Appearance panel renders. Progress, avatar customization and accepted-friend pickers mount on demand. `OnlineLobby` uses the saved profile and contains no profile form, milestone collection or full rule editor. Its roster can send friend requests, and matching Add a bot/Invite friends buttons own seat filling. Room-rule details open the shared account modal.

`InvitationNotifications` stays outside the current route, displays non-blocking Accept/Decline notices and uses one short `notification` chime without starting audio or waiting for playback. Requests remain accessible in Friends after dismissing a popup. Invitations expire after two minutes and survive transient disconnects; reconnecting presence replays still-valid invitations. A new popup never steals keyboard focus. Joining another table while already playing requires the explicit Leave and join action.

The online hook keeps an active room in sessionStorage, with a persistent random device identity in localStorage. On reconnect it rejoins with that identity. New devices cannot join a started game. Rejoining restores the existing seat. If the previous transport still looks connected during a refresh, the known device takes over the seat atomically: its old socket loses membership before receiving a seat-moved notice. A delayed old disconnect cannot evict the new connection. Deliberate leave and kick clear the saved membership. Requests time out after six seconds; never leave a busy control waiting on an unbounded acknowledgement.

Membership changes keep hosting with a connected human. A returning former host does not displace an existing connected host; if everyone was away, the first returning human receives control. Bots never take over host-only decisions. Rejoining also schedules the normal paced bot loop when the current seat is still absent, preventing a stalled round after all-human disconnects. A `room:start` request is rejected before mutation while a round is unfinished, including during a pending wild choice. Cards, rules, round identity, score and deadlines remain intact. A completed result still permits a direct rematch or return to the lobby.

Rules, themes, names and audio preferences are local to the browser. Accepted friendships and pending requests persist on the socket server under the device identity. Storage failure must not prevent play.

The online protocol uses recipient-specific `GameView` snapshots. The server retains the authoritative `GameState`; replies and `room:update` broadcasts include only the recipient's hand, public hand counts, discard history and stock count. Opponent hands, stock faces/identities and another player's unconfirmed wild ID/value are absent, including at the end of a round. Socket membership selects the recipient; client-supplied player IDs never select a view. `gameView.toPresentationGame` supplies stable anonymous card backs for existing presentation/count code. These are presentation-only data: engine actions and bot decisions run on the server's complete state, while client legality only examines the local player's real cards. Clients request the new shape with socket auth `protocolVersion: 2`; older clients receive anonymous backs in the previous packet shape, with the same private data removed. The new client also accepts legacy servers, so either deployment order remains playable; privacy requires the updated socket server. Broadcasts never reuse a host's personalized snapshot for other sockets.

After a completed online round, the host can choose Edit table. The server-authorized `room:return-to-lobby` event preserves the room code, identities, connections, bots and rule preferences, clears round state and clocks, resets readiness, and publishes the lobby to everyone. Guests cannot initiate it and active rounds cannot be interrupted by it. A repeated request in the lobby is harmless. Hosts can then adjust rules or seats and deal without requiring friends to join again. One more round remains available for a direct rematch.

Unfinished local bot rounds save after each engine snapshot under `uno.localRound.v1`. Home offers explicit recovery without running bots or clocks in the background. `savedRound` validates the version, seats, rules, card identities and full deck composition before restoration. Resume preserves hands, deck order, direction, penalties and voluntary-draw state, clears transient action presentation and gives a human turn a fresh 30 seconds. Unconfirmed wild selection is cancelled, so the card can be selected again. Completing or explicitly leaving clears the save; starting a new bot round replaces it. This is one device-local save, independent of online reconnect and completed-round progress. Blocked or full storage never prevents play.

Before a room starts, host rule edits from either the lobby or Settings publish through `updateRoomRules`. Controls wait for acknowledgement and only successful edits become saved preferences; a failed update reports an error. The lobby and initial deal use the published room rules, including after reconnect. Settings shows the actual rules as a read-only summary during a round and for room guests; future-table preferences are edited before joining or dealing. The roster reports actual seats and reconnecting players, and the deal decision precedes optional rules and invitations. Clipboard fallback inputs remain reachable even before joining a room.

The online hook registers presence on connection, refreshes it every minute and publishes saved profile names from any screen. `presence:update` changes only the connected socket’s own room/game name, preserving hands and turn deadlines. Local profile subscriptions likewise update the human seat, including when resuming a saved round. Name changes still notify subscribers and remain available for the session when browser storage is blocked. Shared dialog theme tokens follow the root theme even inside the game arena.

Settings keeps its heading, sidebar or mobile section selector and Done action outside a keyboard-scrollable panel. Related rules use native fieldsets; switching sections resets the panel scroll without discarding profile drafts. Profile edits explicitly distinguish unsaved names, and audio controls subscribe to preference changes while open. Results likewise scroll inside a bounded body while rematch/home actions remain visible. Bot setup discloses optional rule editing and seeds crew portraits with the same `player_<index>` identities as local rounds.

## Verification

Use `check:audio` for gesture-resume races, expired feedback, mute, hidden tabs, offline fallback and recorded-sample signal levels. Use `check:game` for immutable transitions, deck conservation, wild color validation, UNO penalties, and simulated completed rounds. Use `check:multiplayer` against a running socket server for the actual protocol. The socket watcher explicitly includes `lib/**/*.ts` and `types/**/*.ts`; engine edits must restart that process too. Live socket checks cover opening action penalties and direction, so a stale development server cannot silently pass. Run lint, type checks, and a production build. Browser checks should cover home, local setup, a six-seat table, a large hand, a wild picker, settings, room creation, and reconnect after refresh at desktop and phone widths.

For rare near-finish layouts, `.impeccable/review/play-feedback/fixture.mjs` provides explicitly seeded local states using the real engine and unique cards. Follow its README, restore the normal socket server afterward, and never deploy the fixture.

No formal test framework is installed. Keep the existing checks lightweight. Ask the owner before introducing a framework or a major architectural dependency.
